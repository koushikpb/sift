# Phase 4 — Action Agent + MCP: Eval Report

**Date:** 2026-07-01
**Gate:** agent evals on the 50-item eval-set-v1 — end-to-end task success, flag false-negative
rate, trajectory validity, refusal correctness; **HITL confirmation gate + citation groundedness as
hard invariants**. P4 has no pre-registered task-success threshold (unlike P3's +0.05 rule); it
passes by reporting the agent evals with the hard invariants holding and a written failure-mode
taxonomy. **Result: PASS — hard invariants hold; agent capabilities clean; the only real misses are
inherited Layer-1 retrieval-localization cases.**

## What the numbers say (per grader, completed items)
- **flag_match: 19/19 (100%), flag-FN = 0.** Every risk item that completed surfaced its expected
  playbook position. This validates the C1 fix (objective-driven playbook selection + missing-clause
  path) — the classify-label-keyed design would have scored ~1/25 here.
- **refusal: 2/2 (100%).** The single raw "refusal miss" (`refusal_049`) was a NIM timeout, not a
  real over-answer — refusal correctness is perfect on completed items.
- **span_match: 12/18.** The **6 real (non-transport) failures are all here** — retrieval did not
  surface the gold clause into top-k, so the citation didn't overlap the gold span. This is the
  inherited **Layer-1 retrieval-localization ceiling**, not an action-layer defect; groundedness
  stayed **1.0** (when the agent cited, it cited a real span — it never hallucinated).
- **groundedness 1.0 / 0 HITL breaches across ALL 50** — model-independent hard invariants held
  even through the transport failures.

## Toolset (6 over MCP)
`retrieve_clause` (Layer-1 RAG wrapper), `extract_fields`, `classify_clause` (the P3 LoRA, over a
JSON-Schema'd Python bridge), `flag_risks` (+`check_playbook`), `draft_redline`, `export_memo`
(the only **write** tool, HITL `confirm`-gated). Exposed via an MCP stdio server; the sample client
(`core/src/mcp/sampleClient.ts`) lists all six tools over the transport (verified). Quickstart:
`docs/mcp-quickstart.md`.

## Method (deterministic + honest)
- **Agent:** deterministic `reviewContract` trajectory — `retrieve_clause → check_playbook →
  (classify_clause) → flag_risks → draft_redline? → export_memo(preview)`; refuses and short-circuits
  when a clause is ungrounded and no playbook position applies. Deterministic so the trajectory is
  reproducible and the gate is stable.
- **Playbook selection from the objective** (the review *request*), not from the answer: explicit
  `(playbook requires X)` tag for missing-clause items, a curated ContractNLI-hypothesis→position map
  for deviated items. Deviation/absence is still decided by the LLM judge / retrieval — no answer
  leakage.
- **HITL proven by absence of writes:** the agent-eval never passes `confirm`, and `unconfirmed_writes
  == 0` confirms `export_memo` wrote nothing during the entire run.
- **Retrieval:** `RETRIEVE_MODE=hybrid` (dense + FTS + RRF + cross-encoder rerank) to bound API spend;
  retrieval quality was already validated in P2.

## Environment / NIM capacity queueing (a first-class finding)
At gate time the configured `meta/llama-3.3-70b-instruct` returned **0 bytes in 25–30s repeatedly**,
so the gate ran on the comparable `meta/llama-3.1-70b-instruct` (~7s; documented substitution).

**Post-gate follow-up corrected the root cause: the model was not "down" — it was capacity-queued.**
Re-probing with *long* timeouts (the gate used short ones) showed NIM `GET /models` 200/0.13s while
`POST /chat/completions` for `llama-3.3-70b` with a **one-token** prompt eventually returned **HTTP
200 with content `"ok"` but time-to-first-byte == total == ~114s**. Generating one token is
milliseconds, so the ~114s is **pure scheduling/queue wait, not inference**. It is *variable* (114s
once, then >150s and 90s timeouts on the next calls), and `stream:true` / `max_tokens:8` both got
**0 bytes for the entire window** — proving the wait happens *before* generation starts (the request
sits in NIM's GPU scheduler queue). `llama-3.1-70b` returned in ~7s on the same key. So
`llama-3.3-70b` is **alive but heavily oversubscribed on the shared free tier**: NIM accepts the
connection, parks it in a 100–150s+ queue (often past any sane client timeout), then either 200s or
times out. This matches NVIDIA's documented free-tier behavior (40 RPM / 1000 credits, **no SLA**;
under load requests "hang indefinitely with no error"; the recommended fix for consistent throughput
is self-hosting via Brev, not the shared Build endpoint).

**Takeaway:** the `0-bytes-then-timeout` symptom on a NIM 70B is a **capacity/queue signal, not an
outage** — confirm with `curl -m 180`; if it 200s slowly, it was queued. Hardening applied during the
gate: `resolveTimeoutMs` (`LLM_TIMEOUT_MS`, default 45s) + `maxRetries: 1` on all NIM clients (commit
`da150c8`) so a queued call fails fast and the per-item degrade path continues instead of hanging
~10 min (the SDK default). Waiting out the queue (timeout ≥180s) is impractical for a 50-item serial
run under 40 RPM; `llama-3.1-70b` is the pragmatic substitute, or retry `llama-3.3` off-peak.

## Failure-mode taxonomy
1. **NIM transport fragility (11/50, dominant).** Free-tier capacity queueing (`llama-3.3-70b`
   parked 100–150s+ before scheduling, hence the substitution) + intermittent 429s/timeouts under
   load. Root cause is shared-pool oversubscription, not our code or an outage (see "NIM capacity
   queueing" above). Mitigation: bounded timeout+retry (done); lower `LLM_RPM`; a persistent/batched
   classify worker to shorten the run (see Perf); a clean re-run off-peak (or on `llama-3.1-70b`) for
   tighter headline numbers.
2. **Span-localization retrieval miss (6/50).** Gold clause not surfaced into top-k → citation
   doesn't overlap gold. Inherited Layer-1 ceiling; groundedness unaffected (no hallucination).
3. **Deviation-judge degradation under 429.** The judge returns 429 → degrades to `deviation:false`
   (now visible via stderr logging, commit `da150c8`). Flag *coverage* is unaffected (the flag is
   emitted for the matched position regardless); deviation *precision* is reduced on those items.
4. **Missing-clause detection depends on retrieval refusing.** If retrieval surfaces an irrelevant
   clause instead of refusing, the flag is still emitted for the objective's position (coverage
   holds), but as a present-clause deviation judgement rather than an absence finding.

## Perf note
The run took ~25 min because the agent spawns a fresh Python process and reloads the Legal-BERT LoRA
per clause (~35 grounded items). A persistent classifier worker (or pre-batching clause
classification) would cut this to a few minutes — recommended before scaling the eval set.

## Reproduce
```
make db-up
set -a; . ./.env; set +a
make clf-extract                 # regenerate data/processed/cuad_clf/label_map.json (classify_clause loads it)
cd core && npm run load          # ensure the corpus + eval-set docs are loaded + embedded
LLM_MODEL=meta/llama-3.1-70b-instruct LLM_TIMEOUT_MS=30000 RETRIEVE_MODE=hybrid make agent-eval   # -> evals/reports/p4_agent.json
cd core && npx tsx src/mcp/sampleClient.ts <doc_id>   # MCP handshake + a sample tool call
```
